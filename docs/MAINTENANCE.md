# 持续更新流程

任何时候有新进展，都可以直接交给Codex；不要求等到固定周期。本仓库只提供复核清单，没有创建提醒或后台任务。

## 新增

1. 在 `inbox/` 暂存允许入库的文字，附陈述日期和来源。客户文件与凭据不要放入。
2. 给新证据分配S编号，说明是本人原话、现有文件、实测结果还是助手分析。
3. 给每个独立事项分配新事实ID，日期不详留null，按正确状态与证据类别入库。
4. 检查相关旧记录。明确推翻的才关联 `supersedes`；兼容的细化可以并存。
5. 更新资料截止日、版本、CHANGELOG，重新生成并检查差异。

## 纠错

例如旧记录“最新版本4.5.7”不准确，应把它修正为“2026-09-03说明书基线4.5.7”。保留旧记录的错误状态与纠正依据，不把更正日伪装成产品发布日期。用户要求删除个人信息时，删除当前文件还不等于删除Git历史；需要先说明历史范围，再按其具体要求处理，不默认强推重写。

## 验证

```bash
python3 scripts/context.py validate
python3 scripts/context.py build --as-of YYYY-MM-DD
python3 -m unittest discover -s tests -v
git diff --check
```

`data/build-manifest.json`记录事实源哈希、生成检查日和派生文件哈希。同一天同一数据生成结果相同。CI按照清单日期重建，并检查生成文件没有漂移。日常维护应主动选择这次真实复核日期。

## 发布报告

报告新增条数、修正条数、被替换条数、来源类型、受影响上下文、测试结果和仍然缺失的信息。不要只说“已全面升级”，也不要用助手对人的评价代替能力与商业证据。

建议优先补齐：常用称呼 → 公司法定名称与对外定位 → OfficeFlow当前版本和Mac状态 → 实际项目列表 → 商业验证数据 → 最新英语与学习结果。本人不提供的私密字段保持空白。
